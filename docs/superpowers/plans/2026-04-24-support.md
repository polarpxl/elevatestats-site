# Support Section Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `/support` (listing + inline contact form) and `/support/[slug]` (article template) with a 12-article MDX knowledge base, a small set of reusable MDX components (Callout, YouTubeEmbed, Screenshot), and branded defaults for standard markdown elements.

**Architecture:** All article content lives as flat `.mdx` files under `src/content/support/`. A Node-side loader module reads the filesystem at build time, parses frontmatter with `gray-matter`, and exposes typed article metadata for listing + static-params generation. The dynamic `[slug]` route uses `MDXRemote` from `next-mdx-remote/rsc` to render article bodies on the server, with custom components mapped in. The contact form on the listing page is the only client component on either route.

**Tech Stack:** Next.js 16.2.4 (App Router), React 19, TypeScript, Tailwind CSS v4, Framer Motion 12 (already used by shared Nav/FooterCta). Two new dependencies (pre-approved): `next-mdx-remote` and `gray-matter`.

---

## Verified facts

- **Library choice: `next-mdx-remote/rsc` over `@next/mdx`.** `@next/mdx` is designed for MDX-as-routes (MDX files inside `app/`). Our content lives in `src/content/`, separate from routes — that's MDX-as-content, which is exactly what `next-mdx-remote` is built for. Verified against its docs via context7: App Router pattern uses `MDXRemote` in a server component with `parseFrontmatter: true`.
- **`gray-matter` is still needed** because the listing page needs frontmatter for all 12 articles without rendering their bodies. `next-mdx-remote` parses frontmatter only at MDX compile time, which would mean compiling 12 MDX files just to build the listing — wasteful. `gray-matter` parses frontmatter only, in ~3ms total for 12 files. Tiny dep.
- **Routes:** `src/app/support/page.tsx` at `/support`, `src/app/support/[slug]/page.tsx` at `/support/:slug`. `generateStaticParams()` on the dynamic route reads the content folder and returns a slug for each MDX file → all 12 articles render as static pages at build time.
- **Nav's "Support" link:** not currently in the Nav. The Nav has Features / How it works / Pricing / Blog. We won't add Support to the primary nav in this change — it's accessed contextually (Footer "Company → Contact" could later point at `/support`, support links from emails/in-app). If you want Support in the main nav, flag it and I'll add it + the mobile drawer entry.
- **Existing shared primitives:** Nav, FooterCta (with props), Button, Container, Placeholder, links, cn — all reusable.

## Content folder layout: flat, not nested

Flat over category-nested because:
- Slugs become URL paths (`/support/upgrading-to-pro`) — category doesn't appear in the URL anyway (user said "flat filenames, category in frontmatter")
- Single source of truth for category (frontmatter), not duplicated by folder + frontmatter
- `generateStaticParams()` becomes a one-line `readdir`
- Easy to recategorize an article: edit one line of frontmatter

## Loader module: `src/lib/support-articles.ts`

Node-side only (uses `fs`/`path`). Safe to call from server components + `generateStaticParams`.

```ts
import fs from 'node:fs'
import path from 'node:path'
import matter from 'gray-matter'
import { type SupportCategoryId } from '@/lib/support'

const CONTENT_DIR = path.join(process.cwd(), 'src/content/support')

export type ArticleMeta = { slug, title, description, category, order, updated, readTime }

export type ArticleWithContent = ArticleMeta & { body: string }

function readAllArticles(): { meta: ArticleMeta; body: string }[] { ... }

export function getAllArticleMeta(): ArticleMeta[] {
  return readAllArticles()
    .map(a => a.meta)
    .sort((a, b) => a.order - b.order)
}

export function getArticlesByCategory(id: SupportCategoryId): ArticleMeta[] {
  return getAllArticleMeta().filter(a => a.category === id)
}

export function getArticleBySlug(slug: string): ArticleWithContent | null {
  const all = readAllArticles()
  const found = all.find(a => a.meta.slug === slug)
  return found ? { ...found.meta, body: found.body } : null
}

export function getAllSlugs(): string[] {
  return readAllArticles().map(a => a.meta.slug)
}
```

Reads directory once per call — fine at build time (SSG), no runtime cost. If we ever add runtime rendering we can memoize.

## Custom MDX components

**`Callout.tsx`:**
```tsx
type CalloutType = 'info' | 'warning' | 'success'
```
Tinted box (`rounded-card p-4 md:p-5 flex gap-3 ring-1 ring-inset`), coloured icon + body on the right. `info` → brand-blue tint, `warning` → amber tint, `success` → green tint. Inline SVG icons (info-circle, alert-triangle, check-circle). One component, tone swapped via prop.

**`YouTubeEmbed.tsx`:**
```tsx
<div className="my-8 overflow-hidden rounded-card">
  <div className="relative pb-[56.25%]"> {/* 16:9 */}
    <iframe
      className="absolute inset-0 h-full w-full border-0"
      src={`https://www.youtube-nocookie.com/embed/${id}`}
      title={title ?? 'YouTube video'}
      loading="lazy"
      allow="accelerometer; clipboard-write; encrypted-media; gyroscope; picture-in-picture"
      allowFullScreen
    />
  </div>
</div>
```
`youtube-nocookie.com` and `loading="lazy"` as specified.

**`Screenshot.tsx`:**
```tsx
<figure className="my-8">
  <div className="overflow-hidden rounded-card ring-1 ring-black/10">
    <Image src={src} alt={alt} width={width ?? 1600} height={height ?? 900} unoptimized />
  </div>
  {caption && <figcaption className="mt-3 text-center text-sm text-brand-gray">{caption}</figcaption>}
</figure>
```
Uses `next/image` with `unoptimized` so the SVG placeholder renders without needing `dangerouslyAllowSVG` in `next.config.ts`. When real PNGs arrive, drop `unoptimized` for a specific call site or globally.

**Decision flagged for approval:** `unoptimized` on Screenshot keeps the SVG placeholder working with zero config. Tradeoff: no CDN image optimization for real screenshots when they arrive. If that matters, we can enable `dangerouslyAllowSVG` in `next.config.ts` (safe for images from our own `/public`) and drop `unoptimized`. I'm going with `unoptimized` as the safer default; flag if you'd rather invert.

Article body in `[slug]/page.tsx`:
```tsx
<div className="mx-auto max-w-prose">
  <MDXRemote source={article.body} components={mdxComponents} options={{ parseFrontmatter: false }} />
</div>
```
`parseFrontmatter: false` because we've already parsed via `gray-matter` and we pass the body (sans frontmatter) into `source`. This avoids double parsing.

## Styling default markdown elements: individual overrides, not `@tailwindcss/typography`

Declined adding `@tailwindcss/typography`. Two reasons:
1. Extra dependency for ~10 element overrides we'd write anyway
2. Typography plugin's colour/spacing are opinionated and fighting it to use brand-gray / Poppins / Plus Jakarta Sans is more code than just writing the overrides directly

Individual overrides via the `components` prop above keep complete brand control.

`generateStaticParams` on `[slug]/page.tsx`:
```tsx
export function generateStaticParams() {
  return getAllSlugs().map(slug => ({ slug }))
}

export async function generateMetadata({ params }: { params: Promise<{ slug: string }> }): Promise<Metadata> {
  const { slug } = await params
  const article = getArticleBySlug(slug)
  if (!article) return { title: 'Article not found' }
  return {
    title: `${article.title} — Elevate Hockey Stats Support`,
    description: article.description,
  }
}
```

If `getArticleBySlug` returns null (stale link), call `notFound()` from `next/navigation` in the page to render the 404.
